# Directive: LLM Eval System — scoping + build plan

Goal: every LLM call in this repo measured against the hardening-fleet llm-evals bar —
**(1)** a deliberate model-picker with rationale, **(2)** an eval harness scoring response
quality, **(3)** structured schema-validated output, **(4)** logging of cost/latency/failure.
Models judge other models' output; scores are keyed to prompt versions so prompt changes
become measurable regressions instead of vibes.

Status: PR 1 (pilot: viewspec_compile golden-set eval) merged as #424; first win — prompt
v2 scored 16/16 vs v1's 13/16 (#427). PR 2 (rubric-judge mode B: bear_case /
transcript_summary / advisor_next_dollar rubrics + audit runs + judge spot-check) implemented
in this PR — with one adaptation: the "production transcript sink" shipped earlier as
`src/llm/capture.py` (#421, `LLM_CAPTURE_DIR`), so PR 2 reuses it instead of adding a
duplicate `LLM_TRANSCRIPT_DIR` sink. PRs 3–4 pending.
Companion directive: `directives/llm_calls.md` (the canonical-entry-point rule this plan
builds on).

## 2. Target architecture

### 2.1 Three eval modes (one harness)

| Mode | Ground truth | Applies to | Cost |
|---|---|---|---|
| **A. Golden-set deterministic** | Checked-in cases with expected output; graded by code (schema-valid? executes? matches?), judge only on ambiguous divergence | `viewspec_compile` (pilot), `transcript_metadata`, `intake_classifier`, `news_structuring`, extractors | ~free (Haiku target + judge-on-divergence) |
| **B. Rubric judge** | Per-purpose rubric (markdown, versioned); a cheap judge model scores real outputs facet-by-facet with a structured verdict | All prose + structured-judgment purposes (`bear_case`, summaries, advisor memos, lenses) | cents/output (see 2.7) |
| **C. Outcome calibration** | Reality, later (realized KPIs, decision outcomes) | Already live: `grade_bear_cases` / `grade_decisions` / `grade_predictions` | keep as-is |

All three converge on the same storage and the same `(purpose, prompt_version)` key, so the
existing `summarize_by_prompt_version` read side and dashboard sparklines consume eval
scores for free.

### 2.2 Components

```
evals/                              # checked-in eval assets (data, not code)
  golden/<purpose>.json             # golden cases (mode A)
  rubrics/<purpose>.md              # judge rubrics (mode B, PR 2)
src/evals/                          # the harness package
  harness.py                        # dataclasses, scoring math, run orchestration
  store.py                          # eval_runs / eval_case_results writes (loud, not best-effort)
  judge.py                          # judge call + strict verdict parsing (fail-closed)
  viewspec_compile.py               # purpose grader: compile → execute → compare → judge
  bear_case.py                      # (PR 2) rubric grader over data/bear_case/*.json + llm_artifacts
execution/run_llm_evals.py          # CLI: --purpose --mode live|audit --min-score --no-persist
alembic/versions/0083_eval_runs.py  # eval_runs + eval_case_results (+ eval_judge budget seed)
```

Design rules:
- **Evaluate the production path.** Mode A live runs call the real entry point
  (`compile_nl_to_viewspec`, not a re-built prompt), so repair-retry, budget-skip and
  model resolution are all under test.
- **Deterministic before judge.** A judge only fires where code can't decide
  (e.g. compiled spec ≠ expected spec but both valid — is the difference material to the
  question?). Exact matches never spend judge tokens; hard failures never need them.
- **Judge is a first-class purpose.** `eval_judge` gets an `LLM_MODELS` pin
  (Haiku 4.5 — narrow schema-bound verdict task; rationale comment in the table), its own
  budget row, ledger attribution, and — when its prompt changes — its own
  `prompt_versions` bump. Escalation path: per-purpose judge-model override in the grader
  config if Haiku agreement spot-checks come back weak (expected for `advisor_*`).
- **Fail closed.** Unparseable judge verdict ⇒ case scored 0/failed and the raw verdict
  text persisted — never silently passed.
- **Versioned everything.** An eval run records `prompt_version` (target),
  `golden_set_sha`, target `model`, `judge_model`, `git_sha`. Two runs are comparable iff
  you can see what differed.

### 2.3 Storage (migration 0083)

Two tables, modeled on 0058's conventions (naive-UTC datetimes per repo convention):

- `eval_runs` — one row per harness invocation: `run_id` (uuid hex, **also passed as
  `call_llm(run_id=)`** so `llm_calls` rows join back for real cost/latency), `purpose`,
  `mode`, `prompt_version`, `model`, `judge_model`, `golden_set_sha`, `n_cases`, `n_pass`,
  `avg_score`, `started_at`/`finished_at`, `git_sha`, `notes`. Index `(purpose, started_at)`.
- `eval_case_results` — one row per case: `case_id`, `question`, `expected_json`,
  `actual_json`, `passed`, `score`, `failure_stage` (`compile`/`execute`/`mismatch`),
  `judge_verdict` (raw JSON), `judge_rationale`, **`prompt_text`, `response_text`** (full
  transcript — eval volume is tiny, so unlike production `llm_calls` we store text, which
  is what makes failures debuggable and judges auditable), `latency_ms`, `created_at`.

Bridge: each run also writes one `prompt_calibration_scores` row
(`scored_by='auto:eval_harness'`, score = run avg) so the existing dashboard calibration
surface and `summarize_by_prompt_version` pick eval results up with zero new read-side code.

### 2.4 Regression evals on prompt changes

Workflow (documented here, mechanized in PR 4):

1. Edit a prompt → bump its entry in `src/llm/prompt_versions.py` (`v1`→`v2`). This is
   already the repo's single bump-point; unregistered purposes get registered on first bump.
2. Run `python execution/run_llm_evals.py --purpose <p>` → new `eval_runs` row tagged `v2`.
3. Compare: `summarize_by_prompt_version(purpose=p)` shows v2 vs v1 side by side
   (count/avg/p25/p50/p75) — the question "is the rewritten prompt actually better?" gets a
   number.
4. Gate: `--min-score 0.8` exits non-zero below threshold (same shape as the validation
   `--gate` precedent, PR #262). Not wired into CI (LLM calls in CI are forbidden /
   monkeypatched); it's a pre-merge manual gate for prompt PRs, runnable from the dashboard
   later.

### 2.5 Transcript + thinking capture

- **Eval transcripts:** full `prompt_text`/`response_text` per case in
  `eval_case_results` (PR 1, done). Judge rationale persisted alongside — the
  explainability we actually need.
- **Production transcripts (PR 2):** opt-in env-gated JSONL sink in `record_llm_call`
  (`LLM_TRANSCRIPT_DIR` set ⇒ append `{called_at, purpose, ticker, prompt, response,
  model, run_id}` to `data/llm_transcripts/YYYY-MM-DD.jsonl`). Default off — prompts
  embed thesis/IR content and the sha-only ledger is a deliberate choice; the sink exists
  for debugging windows and for harvesting audit-mode eval inputs. Retention note: prune
  with the existing data-lifecycle conventions.
- **Thinking capture: limited through the claude-CLI path, defer.** The subprocess uses
  `claude -p --output-format json`, whose envelope returns only `result` + usage —
  thinking blocks are not included. Capturing them would mean switching to
  `--output-format stream-json` and collecting thinking deltas, with two caveats: it
  reshapes the (load-bearing) envelope parser, and current Opus models omit/summarize
  thinking text by default. Verdict: not worth the surgery now; judge rationale +
  full transcripts cover the explainability need. Revisit only if a debugging need
  appears that transcripts can't serve.

### 2.6 Dashboard surface (PR 3)

New lazy panel `evals` in the analytical dashboard (System section), following the
`llm_budgets` panel pattern (`_build_*_panel` + `/api/panel/<name>`):
- per-purpose latest run: avg score, pass rate, n, prompt_version, when, cost (joined from
  `llm_calls` via `run_id`);
- score-by-version comparison strip (reuses `summarize_by_prompt_version`);
- drill-down to failed cases (question, expected vs actual, judge rationale) — the
  evidence-drawer pattern from the alerts work;
- "Run eval" action button per purpose via the established POST `/actions/<name>` + SSE
  job-stream pattern.

### 2.7 Judge cost model

Prices (per MTok, in/out): Haiku 4.5 $1/$5 · Sonnet 4.6 $3/$15 · Opus 4.7 $5/$25.

| Eval | Per-case tokens (in/out) | Per case | Realistic cadence | Monthly |
|---|---|---|---|---|
| viewspec golden run (16 cases: Haiku compile + judge on ~⅓) | compile ~2.5K/0.15K; judge ~1.5K/0.3K | ~$0.004 | per prompt change + weekly | **<$0.50** |
| Rubric judge, Haiku (bear_case-sized output: ~6K in, 0.5K out) | 6K/0.5K | ~$0.009 | 75 tickers × 6 prose purposes weekly | **~$16** |
| Rubric judge, Sonnet (same) | 6K/0.5K | ~$0.026 | only flagship purposes (advisor memos, bear_case), 75×2 weekly | **~$16** |
| Outcome graders (existing) | unchanged | — | weekly cron | unchanged |

Bound: `eval_judge` budget row seeded at **$10/mo, on_exceed='warn'** in 0083 — covers the

deliberate dashboard action. For context, the entire eval program at full build-out costs

## 4. Pilot (PR 1): viewspec_compile golden-set eval

**Why this purpose:** deterministic ground truth (a compiled spec either validates,
executes, and matches intent, or it doesn't), an interactive user-facing path (Ask/Explore
panel), the repo's best-engineered call site (so the harness measures the model+prompt,
not parser flakiness) — and it still exercises the judge layer on near-misses, which is
the architectural proof the other purposes need.

**Grading ladder per case** (`src/evals/viewspec_compile.py`):
1. `compile_nl_to_viewspec(question, db_path, context_tickers)` — the production entry,
   repair-retry included. `status != ok` ⇒ score 0, stage `compile`.
   (`budget_skipped` aborts the whole run — that's configuration, not quality.)
2. `execute_view(spec, db_path)` — must run without raising ⇒ else score 0, stage `execute`.
3. Normalized comparison vs `expected_spec`: tickers/metrics as sets, transform+cadence
   exact, periods exact unless the case opts into `periods_flexible`, `cagr_years` only
   when transform is `cagr`. Match ⇒ score 1.0, no judge spend.
4. Divergence ⇒ Haiku judge (`purpose="eval_judge"`): given question, expected, actual,
   field diff — structured verdict `{equivalent, score, rationale}`. Fail-closed on
   unparseable verdicts.

Run summary → `eval_runs` + per-case transcripts → `eval_case_results` + bridge row →
`prompt_calibration_scores`. Cost/latency of the run joins from `llm_calls` by `run_id`.

**Golden set:** 16 questions across single/multi-ticker, fin/kpi/seg domains, all four
transforms, both cadences, refinement-free phrasing (context-spec refinement cases are a
follow-up — they need a two-turn harness). Tickers/metrics chosen from tokens present in
the production DB so live runs execute against real data.

**How to run:**
```
python execution/run_llm_evals.py --purpose viewspec_compile --repo-root <MAIN repo>
python execution/run_llm_evals.py --purpose viewspec_compile --no-persist   # dry run, JSON to stdout
python execution/run_llm_evals.py --purpose viewspec_compile --min-score 0.8  # gate mode
```

**Live proof run:** recorded in the PR description (run against the production DB after
migrating it to 0082).

## 5. Appendix: broader hardening assessment

Findings against the wider hardening rubric, with a verdict on whether each deserves its
own track.

### 5.1 LLM security / prompt injection — **worth its own track (highest gap)**

Untrusted text flows into prompts in at least four ways today:
1. **WebSearch-fed**: `recent_developments` and `news_structuring` hand the model live web
   tools / web-fetched article bodies. A hostile page is a direct injection vector into
   memo prose and into the news table that later feeds the `material_news` trigger
   (second-order: injected "news" can fire alerts).
2. **Issuer documents**: transcripts, PDFs, IR decks, 10-K text — semi-trusted, scraped at
   scale by the IR auto-fetch pipeline from issuer websites discovered via crawling.
3. **Anchor chaining**: LLM outputs (thesis/bear/IR anchors) are re-embedded into later
   prompts — an injection that survives into an artifact propagates to 7 downstream prompts.
4. **Comment/chat intake**: `process_report_comments` + Ask thread take operator text
   (low risk, single-user, but the pipeline doesn't distinguish).

Mitigations in place: validated-spec execution for viewspec (model never writes SQL; the
NL box is the repo's exemplar), `--max-budget-usd $2` hard cap on the only agentic call
path, allowlisted web tools only, JSON shape validation on trigger classifiers.
Missing: untrusted-content delimiting/spotlighting in prompts, instruction-priority
preambles ("article text is data, not instructions"), injection canaries in eval golden
sets (mode-A cases that embed adversarial instructions and assert they're ignored — cheap
to add to the harness built here), and a written threat model for the news→trigger→alert
chain. **Recommendation: a sec-llm L1/L2 pass as its own track; wire injection canaries
into the eval harness as part of it.**

### 5.2 QA / test strategy — **healthy; targeted fixes, not a track**

Strong: ~1950-test suite, full-suite CI gate, diff-aware ruff/format + pyright ratchet
(broken-ratchet fails closed), established LLM monkeypatch pattern, migration tests.
Gaps: 2 known test-ordering pollutions (budget integration tests; smoke SEC_S1 — both in
memory, both pre-existing), no E2E over the dashboard job-stream actions, no
load/perf testing (acceptable: local-first single-operator). Verdict: fix the two
pollutions opportunistically; no dedicated track.

### 5.3 Observability — **good substrate; one cheap addition**

Strong: `llm_calls` + `source_calls` + budgets + provenance log + SayDo cron. Gaps:
**section-degradation rate is logged but never aggregated** — a purpose silently degrading
(e.g. bear_case's historical ~75% degrade on chatty prose, found by hand) should surface
as a number; the eval audit mode (PR 2/3) plus a weekly rollup of `llm_calls.error` and
`fallback_used` rates per purpose closes this. Latency SLOs don't apply (no service
consumers). Verdict: fold the error/fallback-rate rollup into the PR 3 dashboard panel;
no separate track.

### 5.4 Structured-output hardening — **fold into PR 4**

One shared `parse_json_response(text, required_keys, retry_cb)` helper would replace ~15
divergent fence-strip/parse/except blocks and kill the silent-empty extractor pattern
(`risk_factor_classify` returning `[]` on parse failure is indistinguishable from "no
risks"). The triggers' retry-with-feedback pattern is the proven template.

### 5.5 Model-picker completeness — **one-line fixes, fold into PR 2**

Register `decision_audit`, `macro_scenario`, `portfolio_macro_stress` in `LLM_MODELS`
(they fall through to default with a warning today); decide whether lens models migrate
into the table or stay per-lens (recommend: stay, but emit them under a `lens:` namespace
note in the table comment so the registry remains the single reviewable surface).
