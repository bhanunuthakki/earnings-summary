# SEC ingestion performance and recovery — October 3, 2026

The canonical Windows SEC task started at 02:00 PDT and remained CPU-active beyond its registered two-hour limit. Nonblocking Python stack samples identified two expensive paths: repeated CompanyFacts parsing/serialization in live fact admission, and `_load_complete_candidates` in financial resolution. This was finite repeated work, not a network wait or an exclusive screen reservation.

## Evidence and correction

- The live matcher created a fresh document cache for each fact and repeatedly serialized the whole source. A ticker-scoped context now retains one verified source/issuer, bounded ladder work and bounded accession candidates. Every fact still verifies raw bytes, content-addressed location, current issuer/binding/scope and the complete admission decision. A synthetic 1.5 MB source with 48 admissions fell from 4.734 seconds to 0.322 seconds. Complete ordered match-ledger bytes and SHA remained identical; parsing, serialization and first-rung walks fell from 48 to 1. Large candidate populations are fully evaluated and are not retained beyond the cache bound.
- The actual Windows SQLite plan drove successor subqueries from every link of a fact table, before selecting the relevant predecessor. Successor-first CROSS joins preserve the inner-join predicates and use the existing financial supersedes index. Migration 0050 adds the missing nonunique KPI supersedes index. With 5,000 unrelated links, complete query rows stayed identical while work fell from about 155,000 SQLite steps to 105–107. Temporal cutoff, uncaptured successor, latest revision and complete candidate-set tests remain required. [SQLite's optimizer contract](https://www.sqlite.org/optoverview.html#manual_control_of_query_plans_using_cross_join) documents this loop-order behavior.
- The supervisor previously relied only on Task Scheduler owner exit. It now enforces the checked SEC task XML's finite ExecutionTimeLimit for scheduled SEC runs. Expiry closes the managed child tree, returns 124 and records failed/incomplete health and journal evidence without replay. When attribution is available, canonical run accounting marks only the exact operation-linked SEC attempt failed. Missing or ambiguous attribution stays explicit and does not trigger a broad stale sweep. Other jobs and manual execution keep their existing contracts.

The scheduler event log confirms a genuine schedule-triggered launch and later definition enabled-state changes. Its failure to enforce the current two-hour limit is observed; the internal scheduler cause is not established. The application deadline removes reliance on that missing enforcement. A synthetic scheduler diagnostic did not establish the original failure mechanism; it left no test task or process.

## Recovery and release state

The owner requested diagnosis and repair, followed by deployment and the service performance backtest. The overdue task was stopped through its registered owner after preserving logs and process identities. All recorded children exited. Canonical `end_run` changed that exact attempt from in_progress to failed under the SEC and database write locks. Eighteen successful per-company timing receipts remain retained. Recovery did not change financial rows, erase source evidence or automatically refetch the universe. The interrupted run is incomplete.

Sol 6.1 review and complete release/native checks are required before deployment. The prior Company Desk fix and migration 0049 remain part of the release; migration 0050 adds only an index. Deployment must preserve a fresh stable database snapshot, complete resolution ledger and current-selection hashes, foreign-key/integrity checks, exact source/runtime bytes, existing junctions and owner/scheduler configuration.

The live backtest covers application services, eight screens at both supported widths, Company Desk and Audit recovery/cancellation, and the deterministic Explore workbench. It does not claim an investment-strategy backtest or source-data completeness. The next genuine weekly SEC execution supplies recurrence evidence; the existing operational monitor is the verification owner. No provider job is manually replayed to manufacture that evidence.
